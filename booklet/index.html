1. The toolchain

Three tools cover everything:

  • rustup installs and switches compiler versions (stable, beta, nightly) and components. It's similar to pyenv.
  • cargo is the build tool, package manager, test runner and doc generator. It does the jobs of go build, go mod, CMake and pip at once.
  • rustc is the compiler. You'll almost never call it directly; cargo does.

Libraries are called crates and come from crates.io. Read any crate's documentation on docs.rs.

CommandWhat it does
cargo new nameCreates a project with Cargo.toml and src/main.rs, and runs git init
cargo checkType-checks without producing a binary. The fastest feedback loop; use it constantly.
cargo runBuilds a debug binary and runs it. Arguments after -- go to your program.
cargo build --releaseOptimized build in target/release/. Usually 2× faster than debug for simple arithmetic loops, and 10× or more for code built on iterators and small functions, which only become fast once the optimizer inlines them.
cargo clippyThe linter. It catches bugs and suggests the idiomatic version of your code.
cargo fmtThe formatter, like gofmt. Everyone uses the default style.
cargo testRuns unit, integration and documentation tests (Day 17).
cargo doc --openBuilds HTML docs for your code and every dependency, available offline.
rustup doc --bookOpens The Rust Programming Language offline.

A plain cargo run only works while the package has exactly one binary. As soon as src/bin/ contains a file, cargo can't guess which program you mean, so you pass --bin every time. If you want a default, add default-run = "day01" under [package] in Cargo.toml.

Editions let Rust make breaking syntax changes without splitting the ecosystem. Each crate picks its edition, and crates of different editions link together without problems. You'll only use 2024.

2. Bindings: let, mut and shadowing

let x = 5;          // immutable by default
let mut y = 10;     // mutation is opt-in
y += x;

let x = x * 2;      // shadowing: a brand-new binding named x
let spaces = "   ";
let spaces = spaces.len();   // may even change type: &str → usize

const MAX_POINTS: u32 = 100_000;   // compile-time constant, type required, SCREAMING_CASE
static GREETING: &str = "hi";      // one fixed memory location for the whole program
Coming from C++

let is roughly const auto, and let mut is auto. Making immutability the default reverses C++'s habit. Shadowing is not reassignment. It's like declaring a same-named variable in an inner scope, except Rust allows it in the same scope. The old x keeps its own memory and value until the end of the block; only the name now refers to the new variable. Anything that already pointed at the old one keeps seeing the old value. That includes references (&x, Rust's checked pointers, covered on Day 3) and closures that captured it.

let x = 5;
let r = &x;          // reference to the first x
let show = || x;     // closure that captured the first x
let x = "five";      // a second, unrelated variable named x
println!("{x} {r} {}", show());   // five 5 5
Coming from Go

There's no := vs = distinction. let always creates a binding and = always assigns to an existing mut one. Unused variables are warnings, not errors; prefix the name with _ to silence them.

Coming from Python

Shadowing looks like rebinding a name to a new type, as Python allows, but every binding is statically typed. The compiler always knows the type of each x.

Literals can carry a suffix (5u8, 2.0f32) and underscores (1_000_000). Hex, octal, binary and byte literals are 0xff, 0o77, 0b1010 and b'A'.

No implicit numeric conversions

let a: i32 = 7;
let b: i64 = 3;
// let c = a + b;          // error: mismatched types
let c = a as i64 + b;      // `as` casts. It can silently truncate or wrap: 300 as u8 == 44
let d = i64::from(a) + b;  // lossless conversion; compiles only if it can never fail
let e: u8 = u8::try_from(300_i32).unwrap_or(u8::MAX);  // checked conversion that can fail

Prefer From where it exists. Reach for as mainly for float↔int and for indexes (i as usize), and remember that it never complains.

Overflow is defined behaviour

Different from C++

In C++, signed overflow is undefined behaviour. In Rust it is always defined: a debug build panics with attempt to add with overflow, and a release build wraps around. When overflow is a real possibility, state the behaviour you want explicitly:

let x: u8 = 250;
x.checked_add(10)     // None (Some(v) if it fits)
x.wrapping_add(10)    // 4
x.saturating_add(10)  // 255
x.overflowing_add(10) // (4, true)

A u8 holds 0 to 255. The true result of 250 + 10 is 260, which doesn't fit. All four methods compute the same addition; they differ only in what to do when the true result is out of range. When it fits, they all agree: 250u8.checked_add(5) is Some(255), wrapping_add(5) and saturating_add(5) are 255, and overflowing_add(5) is (255, false).

MethodReturnsOn overflowUse it when
checked_addOption<u8>None; you must handle that caseOverflow means bad input or a bug, such as sizes, offsets, money, or a length read from a file
wrapping_addu8Wraps modulo 2⁸: 260 − 256 = 4Wrapping is the intended maths, as in hashes, checksums, random number generators and ring-buffer indexes
saturating_addu8Clamps to the type's limit, 255Values that should stop at a limit, such as volume, progress, health points or retry counters
overflowing_add(u8, bool)The wrapped value, plus trueYou need both the result and the carry, as in big-number or multi-word arithmetic

How each one looks in practice

// checked: Option forces you to decide what None means
let total = 250u8.checked_add(10).unwrap_or(u8::MAX);     // a fallback value
match len.checked_mul(size) {                             // or branch on it
    Some(bytes) => allocate(bytes),
    None => return Err("buffer too large"),               // Day 8 covers this properly
}

// wrapping: deliberate modular arithmetic, the FNV-1a hash step
hash = (hash ^ u32::from(byte)).wrapping_mul(16_777_619);

// saturating: unsigned subtraction that stops at zero
let remaining = budget.saturating_sub(spent);              // 3 - 5 gives 0, not a panic

// overflowing: add two 128-bit numbers stored as (hi, lo) pairs of u64
let (lo, carry) = a_lo.overflowing_add(b_lo);
let hi = a_hi + b_hi + u64::from(carry);                  // From<bool>: true is 1

Signed types, subtraction and other operations

Each method family exists for every integer type and covers most operations: add, sub, mul, div, rem, pow, neg, abs, shl and shr. A few cases that surprise people:

127i8.wrapping_add(1)      // -128   two's complement wrap past i8::MAX
127i8.saturating_add(1)    // 127
3u8.wrapping_sub(5)        // 254    unsigned underflow wraps to the top
3u8.saturating_sub(5)      // 0
10u32.checked_div(0)       // None   no division-by-zero panic
i32::MIN.checked_div(-1)   // None   the result, 2³¹, doesn't fit in i32
2u32.checked_pow(40)       // None

And plain +?

Plain operators are for when you are confident the result fits. If you're wrong, a debug build stops with attempt to add with overflow at the exact line, and a release build wraps silently, because checking every operation costs speed. To keep the checks in release builds, add this to Cargo.toml:

[profile.release]
overflow-checks = true

Rule of thumb: use plain operators by default. When a value comes from outside your program or could plausibly be large, pick one of the four methods, and the name of the method tells the next reader what you intended.

Array indexing is bounds-checked too. Reading out of range panics instead of corrupting memory. Safe Rust has no undefined behaviour at all; that's the language's central promise.

4. Everything is an expression

This is the biggest syntax shift from C++, Go and Python. A block { … } evaluates to its last expression, as long as that expression has no trailing semicolon. A semicolon turns an expression into a statement whose value is ().

let z = {
    let t = 3;
    t * t           // no semicolon → the block's value is 9
};

// if is an expression, so there's no separate ternary operator
let parity = if z % 2 == 0 { "even" } else { "odd" };

// loop can return a value through break
let mut n = 0;
let first_square_over_50 = loop {
    n += 1;
    if n * n > 50 {
        break n * n;
    }
};

// while works as you'd expect
while n > 0 { n -= 1; }

// for iterates over anything iterable. Ranges are half-open by default.
for i in 0..3 { print!("{i} "); }     // 0 1 2
for i in 0..=3 { print!("{i} "); }    // 0 1 2 3
for i in (0..10).rev().step_by(3) { print!("{i} "); }  // 9 6 3 0

for (i, ch) in "héllo".chars().enumerate() {
    println!("{i}: {ch}");            // iterates Unicode chars, not bytes
}

// labels break out of nested loops, like Go
'outer: for x in 0..10 {
    for y in 0..10 {
        if x * y == 42 { println!("{x}×{y}"); break 'outer; }
    }
}

Conditions must be bool. Writing if n { … } with an integer is a type error, which removes a whole category of C bugs. The parentheses around conditions are optional, and leaving them out is idiomatic. The braces are mandatory.

5. Functions and formatting macros

fn add(a: i32, b: i32) -> i32 {
    a + b               // implicit return of the final expression
}

fn clamp_to_byte(v: i32) -> u8 {
    if v < 0 { return 0; }      // `return` is for early exits
    if v > 255 { return 255; }
    v as u8
}

Parameter and return types are always written out; inside function bodies, types are inferred. This is a deliberate choice: function signatures are the contract, so they stay explicit. Function names use snake_case and types use CamelCase. The compiler warns when you don't follow these conventions.

Anything ending in ! is a macro. println! is a macro so it can take a variable number of arguments and check the format string at compile time.

6. Just enough match and Option

Exercises 2 and 3 need these two tools. Day 6 covers them in depth; this section is the working subset you need today.

match: a switch that must cover every case

fn size(n: u32) -> &'static str {
    match n {
        0 => "none",
        1 | 2 | 3 => "a few",      // | means "or"
        4..=9 => "several",        // an inclusive range
        _ => "many",               // _ matches anything: the catch-all
    }
}

fn quadrant(x: i32, y: i32) -> &'static str {
    match (x >= 0, y >= 0) {       // match on a tuple: both values at once
        (true, true) => "I",
        (false, true) => "II",
        (false, false) => "III",
        (true, false) => "IV",
    }
}
// size(2) is "a few", quadrant(3, -1) is "IV"
  • Arms are tried from top to bottom, and the first one that matches wins. Put specific patterns before general ones.
  • A match must cover every possible value. Remove the _ arm from size and it won't compile: error[E0004]: non-exhaustive patterns: `10_u32..=u32::MAX` not covered. quadrant needs no _ because its four arms already cover every combination of two bools.
  • match is an expression. Every arm must produce the same type, and the whole match can be a function's tail expression, as in both functions above.
  • Inside a tuple pattern, _ ignores just that position: (0, _) means "the first value is 0, and the second can be anything."
Coming from C++ and Go

Unlike switch, arms never fall through, so there's no break. The compiler also rejects a match that misses a case, which is what makes it safe.

Option: a value that might be missing

Methods like checked_add return an Option<u8>. It's always one of two things: Some(value) when there is a value, or None when there isn't. You can't use it as a plain number. The compiler makes you deal with the None case first:

let r = 250u8.checked_add(5);   // Some(255)
let v: u8 = r + 1;              // error[E0369]: cannot add `{integer}` to `Option<u8>`
Coming from Go, C++ and Python

This plays the role of Go's v, ok := …, C++'s std::optional and Python's None. The difference is that you can't forget to check: the value is only reachable through one of the patterns below.

These are the four ways to get the value out, each a complete program fragment:

// 1. match: handle both cases explicitly
match 250u8.checked_add(5) {
    Some(v) => println!("fits: {v}"),   // v is a plain u8 inside this arm
    None => println!("overflow"),
}

// 2. match used as a value
let x = match 250u8.checked_add(5) {
    Some(v) => v,
    None => 0,
};

// 3. if let: you only care about the Some case
if let Some(v) = 200u8.checked_add(50) {
    println!("{v}");                    // 250
}

// 4. unwrap_or: give a fallback value
let total = 250u8.checked_add(10).unwrap_or(u8::MAX);   // 255

let … else: get the value or leave

When the rest of a function only makes sense if a value exists, use let … else. If the pattern doesn't match, the else block runs, and it must leave the current flow with return, break or continue:

fn label(a: u8, b: u8) -> String {
    let Some(sum) = a.checked_add(b) else {
        return "overflow".to_string();  // must match the function's return type: String
    };
    format!("sum is {sum}")             // sum is a plain u8 from here on
}

fn main() {
    println!("{}", label(1, 2));        // sum is 3
    println!("{}", label(250, 10));     // overflow
}
Common mistake

return leaves the enclosing function, so its value must match that function's return type. Inside main, which returns (), return "overflow".to_string(); fails with error[E0308]: mismatched types. There you'd write println!("overflow"); return;. Inside a loop, use break or continue.

You'll also see .unwrap() and .expect("why"). They return the value, or panic on None. They're fine for quick experiments, but don't rely on them in real code.

Printing tuples and Options

{} only works for types with an obvious user-facing format, such as numbers and strings. Tuples and Options need the debug format, {:?}:

let pair = 250u8.overflowing_add(10);
println!("{}", pair);        // error[E0277]: `(u8, bool)` doesn't implement `std::fmt::Display`
println!("{pair:?}");        // (4, true)
println!("{:?}", 250u8.checked_add(5));   // Some(255)

let (value, wrapped) = pair; // or take the parts out and print them normally
println!("{value} {wrapped}");             // 4 true

Ownership

Every value in Rust has exactly one owner, and the value is freed when its owner goes away. Three rules, checked at compile time, replace both the garbage collector and manual delete.

Time 1½–2 hoursFolder day02/Book chapter 4.1

By the end of today you can

  • explain what a String is in memory and why assigning one moves it
  • tell which types are copied and which are moved
  • pass ownership into and out of functions
  • predict exactly when a value is dropped (freed)
  • read the E0382 "use of moved value" error and fix it two ways

1. The problem ownership solves

Any program that uses heap memory has to answer one question: who frees it, and when? Each language you know answers it differently.

LanguageWho frees heap memoryWhat can go wrong
C++Destructors (RAII), or you, with deleteUse-after-free, double free, dangling pointers, leaks. The compiler doesn't check any of it.
Go, JavaA garbage collector, at run timeSafe, but with GC pauses and memory overhead, and nothing tells you when a file or socket gets closed
PythonReference counting, plus a cycle collectorSafe, but every object carries a count, and cycles need the collector
RustThe single owner, at the end of its scope, worked out at compile timeMistakes become compile errors. There's no run-time cost.
Coming from C++

If you know RAII, you already know half of this. Rust takes RAII and makes it the only option, then adds a compiler check that nobody uses a value after its owner has given it away or freed it.

2. What a String looks like in memory

On Day 1 you used &str literals, which point at text compiled into the binary. A String is different: it owns a buffer on the heap that it can grow. The String value itself is three machine words, 24 bytes on your machine, and the text lives on the heap:

  stack: the String value         heap: the buffer it owns
  ┌──────────┬──────────┐         ┌───┬───┬───┬───┬───┐
  │ ptr      │ ─────────┼───────▶ │ h │ e │ l │ l │ o │
  │ len      │ 5        │         └───┴───┴───┴───┴───┘
  │ capacity │ 5        │
  └──────────┴──────────┘

These are the String operations you'll need today:

let mut s = String::from("hello"); // a new String holding a copy of the literal's text
let empty = String::new();         // empty; no heap buffer yet
s.push('!');                       // append one char
s.push_str(" world");              // append a string literal
s.len()                            // length in bytes
s.capacity()                       // bytes the buffer can hold before it must grow
s.as_ptr()                         // address of the heap buffer; print it with {:p}
let t = format!("{s}?");           // format! builds a new String

3. The three rules

  1. Each value has an owner, which is a variable, or a field of something that is itself owned.
  2. A value has exactly one owner at a time.
  3. When the owner goes out of scope, the value is dropped. Its memory and any other resources it holds, such as a file handle, are freed immediately and deterministically.

Everything else today follows from these three rules.

4. Moves

let s1 = String::from("hello");
let s2 = s1;              // ownership MOVES from s1 to s2
println!("{s1} {s2}");    // error
error[E0382]: borrow of moved value: `s1`
  |
  |     let s1 = String::from("hello");
  |         -- move occurs because `s1` has type `String`, which does not implement the `Copy` trait
  |     let s2 = s1;
  |              -- value moved here
  |     println!("{s1} {s2}");
  |                ^^ value borrowed here after move
  |
help: consider cloning the value if the performance cost is acceptable
  |     let s2 = s1.clone();

Here is what let s2 = s1; actually does. It copies the 24-byte header (pointer, length, capacity) into s2. The heap buffer is not copied. Now two headers point at the same buffer, which would normally lead to a double free when both are dropped. Rust prevents that by treating s1 as no longer usable. At the end of the scope, only s2 frees the buffer.

  s1 (moved-from, unusable)       s2
  ┌──────────┐                   ┌──────────┐         ┌───┬───┬───┬───┬───┐
  │ ptr      │                   │ ptr ─────┼───────▶ │ h │ e │ l │ l │ o │
  │ len      │                   │ len   5  │         └───┴───┴───┴───┴───┘
  │ capacity │                   │ cap   5  │
  └──────────┘                   └──────────┘
Coming from C++

In C++, auto s2 = s1; runs the copy constructor (a deep copy), and you have to write std::move(s1) to move. Afterwards, s1 is still a live object "in a valid but unspecified state," and its destructor still runs. In Rust, moving is the default, the moved-from variable is a compile error to use, and no destructor runs for it.

Coming from Go

Assigning a slice or map in Go also copies just the header, but then both variables share the same backing data, and changes through one are visible through the other. Rust forbids that sharing by invalidating the original.

Coming from Python

b = a in Python makes two names for one object, kept alive by a reference count. In Rust, there is only ever one name that owns the value.

5. Copy types: no move, just a copy

On Day 1, let b = a; with integers left a usable. That's because some types are Copy: assigning them makes a full, independent bit-for-bit copy, and the original stays valid.

let a = 5;
let b = a;                 // i32 is Copy
println!("{a} {b}");       // 5 5 ✅

let lit = "hi";
let lit2 = lit;            // &str is Copy: it copies the pointer, not the text
println!("{lit} {lit2}");  // hi hi ✅

let t = (1, 'x', true);
let t2 = t;                // a tuple of Copy types is Copy
println!("{t:?} {t2:?}");  // ✅
Copy (copied on assignment)Not Copy (moved on assignment)
All integers, floats, bool, charString
&str and other shared referencesAnything that owns heap memory or another resource
Tuples and arrays made only of Copy typesA tuple containing a String, such as (String, i32)

The rule of thumb: a type is Copy if all its data is inline and dropping it needs no cleanup. Copying a String bit by bit would leave two owners of one buffer, so it can't be Copy.

6. Clone: an explicit deep copy

let s1 = String::from("hello");
let s2 = s1.clone();       // allocates a NEW heap buffer and copies the bytes into it
println!("{s1} {s2}");     // hello hello ✅. Each one owns its own buffer.

Rust never deep-copies behind your back. Whenever heap memory gets duplicated, the word clone appears in the code, so expensive copies are easy to find. It's the opposite of C++, where auto s2 = s1; quietly allocates.

Cloning is not wrong, and at this stage it's often the simplest fix. On Day 3 you'll learn borrowing, which removes most of the need for it.

7. Ownership and functions

Passing a value to a function works exactly like assigning it to a variable. Non-Copy values move into the function, and returning a value moves it out again.

fn takes(s: String) {
    println!("takes got {s}");
}                                  // s goes out of scope here → the String is dropped

fn makes() -> String {
    String::from("made inside")    // ownership moves out to the caller
}

fn shout(mut s: String) -> String {  // `mut s`: this function's own variable is mutable
    s.push('!');
    s                              // give ownership back
}

fn measure(s: String) -> (String, usize) {
    let n = s.len();
    (s, n)                         // return the String AND the result
}

fn double(n: i32) -> i32 {
    n * 2
}

fn main() {
    let a = String::from("a");
    takes(a);                      // a moved into takes() and was dropped there
    // println!("{a}");            // error[E0382]: borrow of moved value: `a`

    let b = makes();               // main now owns b
    let b = shout(b);              // b goes in, a new owner comes out (shadowing, Day 1)
    let (b, n) = measure(b);       // get it back together with the length
    println!("{b} has {n} bytes"); // made inside! has 12 bytes

    let x = 21;
    println!("{} {x}", double(x)); // 42 21. i32 is Copy, so x is still usable
}

Look at the note rustc adds when you use a after takes(a):

note: consider changing this parameter type in function `takes` to borrow instead
      if owning the value isn't necessary

Passing a String in and getting it back in a tuple, as measure does, works, but it's clumsy. The compiler's note points to the real fix, which is borrowing. That's tomorrow.

8. Moves and control flow

The compiler tracks moves through every path the program can take:

// Moving in a loop: the first iteration takes the value, so the second has nothing to use
let a = String::from("a");
for _ in 0..3 {
    takes(a);      // error[E0382]: use of moved value: `a`
}                  //   "value moved here, in previous iteration of loop"

// Moving on only one branch: afterwards, the value MIGHT be gone, so it counts as gone
let s = String::from("a");
if some_condition {
    let t = s;     // moved here, on this branch only
}
println!("{s}");   // error[E0382]: borrow of moved value: `s`

// Assigning a new value makes a moved-from variable usable again
let mut s = String::from("a");
let t = s;                  // s moved out
s = String::from("b");      // s owns a new value
println!("{s} {t}");        // b a ✅

// Destructuring moves the parts out (a "partial move")
let pair = (String::from("ann"), 30);
let (name, age) = pair;     // the String moves into name; the i32 is copied
println!("{}", pair.1);     // ✅ the Copy part is still there
println!("{pair:?}");       // error[E0382]: borrow of partially moved value: `pair`

9. Drop: when values are freed

A value is dropped at a precisely defined moment:

  • At the end of its owner's scope, the closing }. Variables in the same scope are dropped in reverse order of declaration, as in C++.
  • When it's moved into a function, it's dropped at the end of that function, unless the function returns it.
  • When a variable is assigned a new value, the old value is dropped immediately.
  • When you call drop(x). There's nothing special about drop; the standard library defines it as fn drop<T>(_x: T) {}. It takes ownership and does nothing, so the value is dropped at the end of that empty function.

Two cases surprise people:

  • Shadowing doesn't drop the old value. As on Day 1, the old variable still exists, just without a name you can use, and it's dropped at the end of the scope like any other.
  • let _ = value; drops immediately, because _ isn't a variable and nothing takes ownership. let _name = value; is a variable (the underscore only silences the "unused" warning), so the value lives to the end of the scope.

Making drops visible (ready-made code)

String doesn't print anything when it's dropped, so to see drops you need a type that does. Copy this into your file as it is. It uses a struct (Day 5) and implements the Drop trait (Day 11). For today, all you need to know is that Noisy("x") creates a value, .0 reads the label inside it, and the value prints drop x when it's freed.

struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("  drop {}", self.0);
    }
}
fn main() {
    let x = Noisy("x");
    {
        let y = Noisy("y");
        println!("inner block ends ({})", y.0);
    }                                   //   drop y
    println!("main ends ({})", x.0);
}                                       //   drop x
